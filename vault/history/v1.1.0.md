# v1.1.0 — Kokoro light engine, Italian by default (2026-09-14)

Package `dist\gb_tts_1.1.0_win64.ts3_plugin`. Request: "usa Kokoro come modello TTS aggiuntivo per risparmiare RAM e risorse, update locale, lingua default italiano".

## What changed
- **Kokoro-82M engine** (`backend/gbtts/engines/kokoro_engine.py`, kokoro-onnx 0.6.1, fp32 ONNX on CPU): voices `ko:if_sara`, `ko:im_nicola` + EN/ES/FR/PT/HI. [[engines-and-models]]
- **The voice selects the engine** (`Controller::setVoice`); `configure` unloads every other engine; engine availability checks never import PyTorch.
- **Automatic backend restart** when a light engine is selected in a process that has PyTorch loaded (`status.torch_loaded`, `Controller::m_memoryRestartTimer`, only when idle): PyTorch never returns its ~2 GB RSS + CUDA context.
- **Qwen loads offline** from the snapshot directory (v1.0 made ~20 HTTP requests per start).
- **Italian UI by default**; the v1.0 `ui/language=auto` saved in the registry is migrated to `it`; Settings offers Italiano/English only.
- Installer downloads Kokoro instead of Supertonic (Supertonic still selectable, downloads on first use); no GPU ⇒ engine Kokoro.
- Tools: `measure_memory.py` (RSS/VRAM/HTTP per engine in a fresh process), bench `--engines kokoro --kokoro-variants`.

## Measured
Memory per engine (fresh process): Kokoro fp32 595 MB / 0 VRAM · Supertonic 514 MB · Qwen 0.6B 2 225 MB + 2.7 GB VRAM · Qwen 1.7B 2 183 MB + 4.7 GB VRAM. All loads: 0 HTTP requests.
Kokoro intelligibility: Whisper CER 0.000 (Sara) / 0.012 (Nicola: "9" for "nove").
Backend e2e through the real protocol: Kokoro-only backend 526 MB RSS, no VRAM; Qwen → Kokoro frees 2 954 of 3 740 MB VRAM before the restart (CUDA context stays).

## Bugs / traps found (root causes)
1. **int8 Kokoro is 7× slower than fp32 on CPU** (RTF 0.35 vs 2.6; dynamic-quant kernels ≈ one core, 8 % CPU load). fp32 default.
2. **`phonemizer.phonemize()` 250 ms per call** (backend rebuilt each call) → cached `EspeakBackend`: 0.1 ms.
3. **ORT memory pattern with dynamic shapes**: every new sentence length re-plans → RTF 3.4 with 2.0× worst chunks; `enable_mem_pattern=False` → steady 5.0–5.1.
4. Kokoro is not streaming → first-clause split (comma/semicolon/colon) so the voice starts after the short clause.
5. Thread count: all cores RTF 5.5, 8 threads 5.1, 6 threads 4.4 → 8 (half of a 20-thread CPU left to games).
7. **ORT thread spinning** burnt 2.2–2.4 cores for a second after every inference and was slower (RTF 5.1 vs 5.6) → `allow_spinning=0`: 0 idle CPU.

## Final latency (backend e2e, 13/13 PASS)
Kokoro first audio 292 ms (348 ms at speed 1.25), 515 MB RSS, no VRAM. Qwen→Kokoro frees 2 995 of 3 800 MB VRAM in-process; the plugin's idle restart then returns the rest (PyTorch RSS, CUDA context) — plugin-side logic, not exercisable without a TeamSpeak client.
6. Test-harness traps (not product bugs): the venv `python.exe` is a launcher — RSS must be read from its child; per-process VRAM is "N/A" under WDDM — use whole-GPU deltas.
