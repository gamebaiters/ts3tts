# v1.3.0 — real-time AI voice changer (2026-09-15)

Package `dist\gb_tts_1.3.0_win64.ts3_plugin` (not installed: TeamSpeak was running). Request: "quando parlo la mia voce passa nel modello e viene modificata in tempo reale, tipo clownfish però figo".

## What changed
- **Live voice (AI)**: MeanVC2 streaming zero-shot voice conversion on the CPU; you talk (PTT/VAD), the channel hears the chosen library voice ~0.3 s later; your real voice is never sent while it is on. Full design, research and numbers: [[voice-changer]].
- Protocol frames `0x03` MIC / `0x04` VC; ops `vc_configure`, `vc_list_targets`, `vc_add_target`; events `vc_status`, `vc_targets`, `vc_target_added`, `vc_stats`. [[backend-protocol]]
- Backend `gbtts/vc/` (service, session, engine, vendored MeanVC2 + WavLM + rotary with NOTICE); `tools/download_models.py --models vc`; weights download lazily on first enable; `requirements.txt` pins einops + safetensors explicitly.
- Plugin: `TtsAudio` voice changer path + reader starvation guard, `LinkWorker::pumpMic`, Controller voice-changer state + tail hold, TtsWindow "Live voice (AI)" section, settings group `voice_changer` (off by default, preset 40ms, monitor off).
- Plugin description mentions Kokoro and the voice changer.

## Bugs found (root causes)
1. Upstream MeanVC2 `run_rt.py` stretches the 40 ms model 1.95× (fixed BN upsampling size) — fixed in our engine.
2. soxr streaming resamplers add 20–60 ms of holdback round trip → `FirResampler3` (−37 ms, same CER).
3. **TTS click on reader starvation** (pre-existing, intermittent): blocks ran dry with an empty raw ring after a full-amplitude sample → decay-to-zero + ramp-in in `readLocked`. Selftest §4 now passes 5/5 consecutive runs (was 1/3).
4. Voice changer ring running dry exactly at a block boundary → 1 058-LSB step → 2 ms reserve before the last delivered block.
5. `test_engine` equivalence first "failed" twice: thread count (kernels) then a re-computed cached embedding (different input) — the code was equal; the test now freezes the embedding and loads at 1 thread.

## Lifecycle regression (host harness, 20 cycles with the real Kokoro backend, FreeLibrary every cycle)
A/B with the v1.2.0 DLL taken from the TeamSpeak plugins folder: identical behaviour — handles 311 → 327 at cycle 2-3 then back to 314 (v1.2) / 316 (v1.3), threads and GDI/USER flat, raw private bytes +0.46 / +0.48 MB per cycle in both, no crash, backend gone ≤ 10 ms after every shutdown. The first 3-cycle run (311 → 327, "FAIL handles") was that one-time pool step, not a v1.3 leak.
30 cycles with the backend and `--trim`: private bytes 13.1 MB at cycle 5 → 13.7 MB at cycle 30 (range 12.7–14.0), i.e. ≤ ~25 KB/cycle inside ±1 MB noise; the harness's second-half slope check (+0.099 > 0.05 MB/cycle) trips on that noise. Bounded, not proven zero; TeamSpeak loads the plugin once per session. Crash test (segv, Kokoro loaded): backend dead 16 ms after the client.
